## 一、專案概觀

模擬 **10 台工具機（SCT-01~10）** 的高頻電流／振動感測，建立一條從「資料擷取 → 儲存 →
AI 偵測 → 剩餘壽命預測 → 戰情室視覺化」的完整預防性維護鏈。

### 規格

| 項目 | 值 |
|---|---|
| 機台數 | 10（SCT-01 ~ SCT-10） |
| 每台感測器 | 7 個（三相電流 + 三軸振動 + 溫度） |
| 取樣率 | **2 kHz**（約 12 萬筆/秒） |
| 實測吞吐 | 約 24 萬筆/5 秒 |
| 累積資料量 | `sensor_readings` 2.1 億筆（20 分鐘滾動保留） |

### 核心能力

| 能力 | 技術 | 狀態 |
|---|---|---|
| 早期異常偵測 | One-Class SVM（頻譜特徵） | 上線 |
| 漸進劣化偵測 | Self-Starting CUSUM | 上線 |
| 剩餘壽命預測 | RandomForest（真實軸承訓練） | 上線 |
| 災難兜底 | 時域絕對門檻跳線 | 上線 |
| 視覺化 | Grafana 五分頁戰情室 | 上線 |

## 三、Phase 1：高頻資料產生

### 實現方式

10 台機台各是一個**獨立 OS 進程**（`multiprocessing.Process`），不是執行緒 —— 這是為了繞過
Python GIL，讓 8 核 CPU 能真正平行產生資料。

**精準計時**：不用 `time.sleep(1/2000)` 累積誤差，改用基準時間 + `next_tick = start + n*interval`
搭配 `time.perf_counter()` 校正。相鄰兩筆同感測器的時間戳嚴格相差 0.5 ms。

**向量化產生**：一次算一批 NumPy 陣列而非逐筆呼叫（`formulas.py`）。

### 物理量公式

| 感測器 | 公式 |
|---|---|
| 溫度 | `N(setpoint, σ)`，裁切在 25.5~26.5°C |
| 電流 | `I_base + A·sin(2π·60·t) + noise`，三相各差 120° |
| 振動 | 三軸各有獨立基礎振幅與相位差，合成幅值落在目標值附近 |

### 故障注入（HTTP 控制 API，port 8080）

| 端點 | 效果 | 用途 |
|---|---|---|
| `POST /danger/<機台>` | 振幅瞬間拉高到危險線 ×1.3 | 驗證即時警報 |
| `POST /degrade/<機台>` | 諧波邊帶 + 振幅隨時間成長（10 分鐘爬滿） | 驗證 AI 提前預警 |
| `POST /normal/<機台>` | 解除 | — |
| `GET /status` | 查全機隊狀態 | — |

POST 類端點都要帶 `Authorization: Bearer <CONTROL_API_TOKEN>`（`GET /status` 免驗證）；
API 預設只綁 127.0.0.1。

**漸進劣化的設計演進**：原本只注入頻譜諧波（振幅幾乎不變），刻意讓「只看均值」看不出來、
只有頻譜分析抓得到。後來接上 ML RUL 時發現模型 57% 靠振幅（`rms_norm`），完全抓不到 ——
因為真實軸承磨損 RMS 會暴增。故補上 `DEGRADE_VIBRATION_AMPLITUDE_GROWTH`，讓劣化同時觸發
**頻譜路徑**與**振幅路徑**，也更接近真實磨損。

### 可靠度設計

- **進程健康檢查**：機台進程死掉會單獨警示（不自動重啟，避免掩蓋問題）
- **本地雙緩衝**：滿 500 tick 或 250 ms 出貨（2kHz 下兩者同時命中）
- **背壓保護**：每台機台專屬 Queue 有容量上限

## 四、Phase 2：資料匯流與儲存

### 高吞吐寫入

**4 條平行 DB 連線**（`NUM_DB_WRITERS`），把 10 台機台輪流分攤。單一連線實測 12~14 萬筆/秒，
追不上模擬器全速；4 條並行實測可達約 25.5 萬筆/秒。

**COPY 批次寫入**：先 COPY 進 temp staging table 再 INSERT SELECT，比逐筆 INSERT 快數倍。

### 斷線自癒

- 寫入失敗**不會**讓 thread 死掉 —— 保留未寫資料、遵守冷卻時間重連
- 資料庫恢復後自動補寫累積的資料
- **背壓**：本地 buffer 到上限就停止抽 Queue，靠 Queue maxsize 頂住，不會把記憶體吃爆

### 儲存層設計

| 機制 | 設定 | 目的 |
|---|---|---|
| Hypertable | chunk 10 分鐘 | 時序分區 |
| 連續彙總 | 1 秒 bucket | Grafana 查彙總表而非原始，才能秒級刷新 |
| 保留政策 | **20 分鐘** | 2kHz 下約 1 GB/分鐘，不可能長期保存 |
| 容量保險絲 | 150 GB | 保留政策失效時的第二道防線（曾把系統碟撐爆過） |

### 資料表

| 表 | 內容 | 保留 |
|---|---|---|
| `sensor_readings` | 逐筆原始（2.1 億筆） | 20 分鐘 |
| `anomaly_scores` | AI 特徵/分數/CUSUM（63,458 筆） | 永久 |
| `rul_predictions` | 三種 RUL + 信賴區間（124,244 筆） | 永久 |
| `machine_vibration_thresholds` | 各機台 ISO 門檻 | 靜態 |
| `cusum_baselines` | CUSUM 基線（含模型指紋） | 永久 |
| `vib_trip_latches` | 跳閘閂鎖 | 永久 |
| `system_health` | CPU/RAM/TPS/延遲 | 永久 |

### 外部資料進線

MQTT（port 1883）訂閱 `iiot/#`，主題格式 `iiot/<device_id>/<sensor_id>`，
payload 為 JSON。真實裝置與模擬器寫進**同一張表**，所以下游全部不用改。

- **認證**：broker 禁止匿名連線，帳密是 `.env` 的 `MQTT_USERNAME` / `MQTT_PASSWORD`。
- **輸入驗證**：device_id／sensor_id 只收英數字與 `_ . : -`；value 必須是有限數字；
  時間戳最多只能比現在晚 5 分鐘。不合格的訊息會被丟棄並印 log。
- **時間戳時區**：建議送帶時區的 ISO 8601（例如 `2026-07-01T19:23:45.125+08:00`）。
  沒帶時區的字串一律當成 `MQTT_NAIVE_TIMESTAMP_TZ`（預設 `Asia/Taipei`）。

## 五、Phase 3：AI 偵測與預測

這是整個專案的核心，四層偵測疊在一起。

### 5.1 訓練與推論分離

**問題**：原本 SVM 在服務啟動時「順便」訓練、只活在記憶體。每次重啟要等 300 秒重訓；
更嚴重的是**重訓後分數尺度會變**（實測離散度差 1.5~3 倍），導致下游的 CUSUM 基線全部失效。

**解法**：

```
sensor_readings ──> trainer.py ──> model_store（Docker volume）
                                        │
                        載入優先 ────────┴──> main.py 推論（重啟不重訓）
```

| 模組 | 職責 |
|---|---|
| `anomaly_detector.train_model` | 訓練演算法（One-Class SVM 本身） |
| `trainer.py` | 訓練流程與策略、CLI |
| `model_store.py` | 存/載/指紋/中繼資料，原子寫入 |

**模型指紋**：由 SVM 的 support vectors、dual_coef、intercept 加 scaler 參數算 SHA256。
CUSUM 基線只有在指紋相符時才會被取用 —— 讓「模型換了、基線卻沿用」在結構上不可能發生。

**實測**：重啟後 60/60 載入既有模型、**0 重訓**。

### 5.2 頻譜異常偵測（One-Class SVM）

對**每台 6 通道**（電流三相 60Hz + 振動三軸 30Hz）各訓練一個模型，學「正常長怎樣」。

| 參數 | 值 | 依據 |
|---|---|---|
| `nu` | 0.05 | 設計上的離群比例 |
| `gamma` | **0.02（固定值）** | 用 `"scale"` 在小樣本下過擬合，held-out 誤報 43.7% |
| 訓練視窗 | 300 秒（約 146 窗口） | 60 秒（56 窗口）樣本太少會過擬合 |
| 特徵窗口 | 4096 點（約 2.05 秒） | 2 的冪，方便 FFT |
| 判定門檻 | `score < -1.0` | 正常資料 ≥ -0.7、真異常 ≤ -2.5，中間有 2 個單位的分離帶 |

**特徵**（6 維）：`mean, std, skewness, kurtosis, thd_ratio, noise_floor_ratio`
外加時域的 `rms, crest`（供 ML RUL 使用）。

**踩過的坑**：服務啟動初期資料剛到窗口數下限就搶先訓練，訓練集會含暖機期的不連續段，
FFT 特徵整組被污染 → 誤報飆到 40%+。修法：訓練前檢查取樣覆蓋率 ≥ 95%。

### 5.3 漸進劣化偵測（Self-Starting CUSUM）

累積「異常分數持續系統性下滑」，而非看瞬時值是否低於某條線。

**演進歷程**（這是本專案最曲折的部分）：

| 版本 | 做法 | 問題 |
|---|---|---|
| v1 | 固定門檻 `h = 8σ₀`，20 筆暖機估參數 | 緩慢劣化 onset 太晚亮；σ₀ 高估時永不觸發 |
| v2 | 門檻衰減到地板 + robust 校準 + 基線持久化 | 跨模型重訓基線失效，誤報 19% |
| v3 | 模型指紋綁定基線 | 誤報降到 0.7%，但仍會累積 |
| **v4** | **Self-Starting CUSUM** | **根治** |

**v4 的原理**（Hawkins 1987）：不預先估參數，而是把每個新觀測用「它之前所有觀測」的
running mean/SD 標準化：

```
T_n = (x_n − x̄_{n−1}) / s_{n−1} × √((n−1)/n)     ~ t(n−2)
U_n = Φ⁻¹( F_{t,n−2}(T_n) )                        ~ N(0,1)
```

**關鍵性質：U_n 是嚴格的 iid 標準常態，與未知的 μ、σ 無關。**

| 設計 | 說明 |
|---|---|
| Welford 線上統計 | O(1) 記憶體、數值穩定 |
| `h = 7.0`（純數字） | 依 ISA-18.2：60 通道機隊告警率 1.0 則/小時（限制 <6） |
| `k = 0.5` | slack，濾掉正常波動 |
| 最少 5 筆才判斷 | 就緒時間 2.5 分鐘（v1 需 10 分鐘） |
| 機率截斷 1e-6 | 單一離群最多貢獻 4.25 < h，**孤立瞬態無法單獨觸發** |
| 告警後凍結基準 | 否則劣化會被 running 統計吸收成「新的正常」而自己消警 |

**驗證（離線）**：對 σ 相差 35 倍的三組資料（N(-0.2,0.1)、N(0.5,0.32)、N(12,3.5)）跑出
**完全相同**的結果（ARL 6079）—— 證明估計誤差確實被數學消除。

**驗證（線上，2026-08-25 逐 10 分鐘）**：

| 時段 | 評分數 | CUSUM 告警 | 告警機台 | cusum 最大 | 版本 |
|---|---|---|---|---|---|
| 12:20 | 360 | 14 | **5** | 3.78 | 舊版（估計參數） |
| 12:40 | 1020 | 28 | **4** | 2.98 | 舊版 |
| 12:50 | 1080 | 15 | **3** | 2.86 | 舊版 |
| **13:00** | 1020 | **0** | **0** | 6.68 | **Self-Starting** |
| 13:10 | 1080 | **0** | **0** | 6.97 | Self-Starting |
| 13:20 | 1020 | **0** | **0** | 4.89 | Self-Starting |
| 13:30 | 1080 | **0** | **0** | 4.79 | Self-Starting |
| 13:40 | 840 | **0** | **0** | 4.73 | Self-Starting |
| 13:50 | 720 | **0** | **0** | 4.30 | Self-Starting |

**連續約 60 分鐘、6,000+ 次評分，0 筆 CUSUM 誤報**（切換前每 10 分鐘有 14~28 筆、
3~5 台機台在告警）。

`cusum 最大值` 這一欄是關鍵佐證：數值在 **4.3~7.0 之間震盪**（門檻 h=7），
代表統計量確實在遊走、不是卡在 0，但**不會單調累積**。13:10 曾逼近 6.97 而未跨過 ——
這種近失是統計上預期會偶爾出現的，正是門檻該有的行為。

期間另有一次計畫性重啟（13:46，調整 WSL2 記憶體設定），重啟後仍維持 0 誤報。

### 5.4 剩餘壽命預測（三種視角）

| 種類 | 追蹤量 | 方法 | 適用 |
|---|---|---|---|
| 電流均值 RUL | 電流均值撞 5.5/6.5% | 線性回歸外推 | 負載漂移類 |
| 頻譜 RUL | thd_ratio 撞 0.05 | 兩段式（CUSUM onset 閘門 + 外推） | 振幅還沒動、頻譜先變 |
| **ML RUL** | RandomForest 直接輸出分鐘 | 監督式學習 | 一般軸承磨損 |

**ML RUL 細節**：

- 模型：RandomForest（120 棵樹），用 **32 顆真實軸承**（PHM2012 17 + XJTU-SY 15）訓練
- 特徵：`[rms_norm, kurt, crest, rms_slope_per_min]`，重要度 `rms_norm` 佔 57%
- `rms_norm` = 現值 RMS / 健康基線（該通道最早 20 筆 RMS 的中位數）
- 目標：分段線性 RUL（上限 250 分鐘）

**信賴區間（ISO 13381-1 要求）**：RandomForest 的每棵樹各是一個獨立預測，
**取樹分布的分位數就得到「免費」的預測區間**，不需重訓或另建模型。

實測：劣化越明顯區間越窄 —— 健康 190~241（寬 51 分）、劣化中 109~139（寬 30 分）。

### 5.5 時域絕對門檻跳線（災難兜底）

三軸 RMS 合成幅值 ≥ ISO 危險線就**強制 CRITICAL，完全不看 AI**。

專門接住「學習型模型失效」的情況 —— 模型沒訓練成功、或不幸在已劣化資料上訓練（學歪基線）。

| 護欄 | 值 | 依據 |
|---|---|---|
| 檢查週期 | 10 秒（**獨立執行緒 + 獨立連線**） | 保險絲不該被昂貴的 FFT/SVM 拖慢或餓死 |
| 去抖動 | 連續 3 輪（30 秒） | API 670 用 1~3 秒延遲濾突波是同一原理 |
| 遲滯 | 0.9 | ISA-18.2 死區防抖動 |
| 閂鎖 | 至人工確認 | ISA-18.2：條件解除與確認缺一不可 |
| 門檻 | 依機台 Class 從 DB 讀（I=4.5 / II=7.1 / III=11.2 mm/s） | ISO 20816 分區 |

**實測驗證**：注入 SCT-07（Class II）→ 合成 RMS 9.293 ≥ **7.1**（非 4.5），
證明分機台門檻真的生效。解除後振動回 0.429 但閂鎖仍在、持續寫 CRITICAL，直到人工確認才復歸。

## 六、Phase 4：視覺化戰情室

Grafana **五分頁**（依 `iiot-tab` tag 自動組成頂部按鈕列，切換時保留 `$device`/`$lookback`/時間範圍）。

| 分頁 | 內容 |
|---|---|
| **① 狀態總覽** | 全機台燈號矩陣、需注意機台、告警明細 |
| **② 機台現況** | 溫度、電流三相、三軸振動 vs ISO（皆折線圖 + 上下限） |
| **③ 早期預警** | thd_ratio、CUSUM、ML RUL + P10/P90、rms_norm、三種 RUL 總表 |
| **④ 告警歷史** | 告警時間軸、異常事件明細（涵蓋全部偵測器） |
| **⑤ 系統健康** | CPU、RAM、TPS、寫入延遲 |

### 燈號矩陣的設計

五種狀態，**純 SQL 即時算出，不需要任何後端狀態表**：

| 燈號 | 條件 |
|---|---|
| 綠 正常 | 回看範圍內無告警 |
| 橘/紅 實心 | 最近 2 分鐘仍在告警 |
| **橘/紅 閃爍** | **回看範圍內曾觸發、現況已恢復** |

「曾觸發過即使已恢復仍閃爍提示」是為了避免**自我復原的間歇性故障被無聲略過**。
回看範圍可用頂部變數調整（1h / 4h / 8h / 24h / 7d），超過就自動轉綠。

閃爍用 SQL 時間模運算（10 秒週期）配合儀表板 5 秒刷新達成 —— Grafana 核心面板本身不支援閃爍。

## 八、能力誠實評估

這一節刻意寫得保守，因為**知道系統的極限比宣稱它多強更重要**。

### 各能力的可信度

| 能力 | 評價 |
|---|---|
| **異常偵測** | ✅ **可靠** —— 32/32 軸承全命中 |
| **漸進劣化偵測** | ✅ **可靠** —— Self-starting 後 ARL 理論值＝實際值 |
| **災難兜底** | ✅ **可靠** —— 不依賴 ML，物理門檻 |
| **RUL（線性外推）** | ❌ **不堪用** —— 誤差 164~610% |
| **RUL（ML）** | ⚠️ **粗估可用，精準不可信** |

### RUL 準確度的分段實測（IMS 獨立測試集）

| 真實剩餘 | 相對誤差中位 | 偏差方向 | ±1.5x 命中率 |
|---|---|---|---|
| 0~30 分 | 266% | **高估 +47 分（危險）** | 0% |
| 30~60 分 | 50% | 高估 +13 分 | 22% |
| 60~120 分 | 66% | 低估 −38 分（保守） | 17% |
| 120~250 分 | 73% | 低估 −115 分 | 8% |

**三個必須誠實面對的結論**：

1. **不能當精準倒數** —— ±1.5x 命中率全程只有 8~22%
2. **偏差方向會翻轉，最危險的是最後關頭** —— 離故障遠時低估（安全），
   進入最後 60 分鐘反而**高估**（給假的安全感）
3. **可靠的是分級不是數字** —— 「健康/開始劣化/進入可行動窗」可信，「還剩幾分鐘」不可信

**實務建議**：以 WARNING（RUL 首次跌破 200 分）當行動觸發，**不要等 CRITICAL**；
看下降趨勢而非咬住絕對數字。

## 九、重要的工程決策與教訓

### 9.1 取樣率：4kHz → 2kHz（瓶頸是 CPU 不是磁碟）

磁碟搬到 NVMe 後一度恢復 4kHz，磁碟寫入沒問題（延遲 0.2~0.4s）。但實測
「4kHz + 完整 AI（60 通道 FFT/SVM）+ 10 個機台進程」會把 8 核 CPU 壓垮：
**機台進程被 CPU 飢餓餓死（10 台死剩 4 台）、吞吐崩到 40%、訓練覆蓋度不足卡死**。

降回 2kHz 後一切正常。Nyquist 從 2kHz 降到 1kHz，60Hz 基頻與 120/180/240Hz 諧波偵測不受影響。

### 9.2 CUSUM 參數估計：從調參到換架構

這是本專案最重要的一課。

**現象**：使用者回報「告警機台逐漸變多」。實測 1→2→3→4 單調上升，但機台實際健康。

**根因**：CUSUM 增量 = `mu0 − score − slack`。只要 mu0 估高超過 slack，
增量長期為正 → **數學上保證單調累積、必定誤報**，且跨過門檻後不歸零、無法自我修復。

**核心是樣本數**：20 筆估均值的 95% 誤差界是 `2σ/√20 ≈ 0.45σ`，而容錯只有 `slack = 0.5σ`
—— **估計誤差幾乎用光整個容錯**。

**文獻佐證**（查了才動手）：控制圖領域早有結論 —— 估計參數的管制圖需要**數百個** Phase I
樣本；m=50 時 80% 使用者拿到的 ARL 落在 87.6~290.4（名目 200），要 m=800 才收斂。

**教訓**：我前兩次都在修 μ₀（中心），但真正壞掉的是 σ₀（離散度）跨重訓被低估 1.5~2.7 倍。
**先查文獻再動手**才找到正確方向 —— 這個問題有標準解（Hawkins self-starting），
不需要自己發明。

### 9.3 告警門檻要換算成機隊尺度

CUSUM 地板一度訂 5σ，理由是「單通道 ARL 938，還算安靜」。**這是錯的** ——
操作員感受到的是整個機隊，**機隊告警率 = 單通道率 × 60 通道**。

| 地板 | 機隊告警率 | ISA-18.2（<6/小時） |
|---|---|---|
| 5σ | 18.6 則/小時 | ⚠️ 超標 |
| 6σ | 5.9 則/小時 | 壓線 |
| **7σ** | **3.1 則/小時** | ✅ 約 2 倍餘裕 |

### 9.4 依國際規範校準參數

| 規範 | 用在哪 |
|---|---|
| **ISO 20816 / 10816** | 振動分區、Trip 設在 C/D 分界、寬頻 RMS 速度 10~1000 Hz |
| **ISA-18.2** | 告警率目標（<6 則/小時/操作員）、死區防抖動、閂鎖與確認語意 |
| **ISO 13381-1** | 預後結果須附信賴區間 → RUL P10~P90 |
| **ISO 13374 / OSA-CBM** | 六層架構 → 盤點出缺第 4 層（診斷）與第 6 層（維修建議） |
| **API 670** | 機械保護系統的定位對照 → 確立本系統是「告警兜底」而非「跳機保護」 |

### 9.5 安全兜底不能靜默失效

實作時域跳線時踩到一個 bug：`LIKE 'V%'` 的 `%` 被 psycopg2 當成參數佔位符而拋
`IndexError`。但我原本只 `except psycopg2.Error`，`IndexError` 逃逸 →
**執行緒直接死掉、之後完全沒有保護且沒有任何警示**。

**安全兜底靜默死亡比沒有這道保險更危險**，因為它讓人誤以為有保護。
修法：捕捉所有 `Exception`，記錄後重連續跑。

### 9.6 磁碟管理

- 20 分鐘保留 + 150GB 容量保險絲（時間保留失效時的第二道防線）
- **vhdx 只增不減曾釀成 SIGBUS 崩潰**：ext4 內實際用 41GB，vhdx 檔卻長到 100GB 把磁碟撐爆
- 根治：`.wslconfig` 設 `sparseVhd=true`；手動回收需 `fstrim` +（提權）`diskpart compact`
- **關機順序**：務必 `docker compose stop --timeout 90` 讓 TimescaleDB 完成 checkpoint，
  否則 SIGKILL 會遺失 WAL、把保留政策設定回滾

## 十、已知限制與待辦

### 🔴 安全（上線前必修）

已修（2026-11）：

| 原本的問題 | 現在的做法 |
|---|---|
| 控制 API 無認證且對外 | POST 需 Bearer token（`CONTROL_API_TOKEN`）；預設只綁 127.0.0.1 |
| 全部使用預設密碼 | compose 不再提供預設密碼，`.env` 沒設定就拒絕啟動（範本：`.env.example`） |
| 5432 對外映射 | 預設只綁 127.0.0.1 |
| MQTT 匿名可寫、無輸入驗證 | 禁止匿名、需帳密；ID／數值／時間戳都會驗證，未來時間戳最多允許 5 分鐘 |
| MQTT 佇列無上限 | 上限 10 萬筆，滿了就丟新訊息並限頻印 log |

仍待處理：

| 問題 | 風險 |
|---|---|
| 容器以 root 執行 | 攻破後風險放大 |
| Grafana 用 DB owner 帳號 | 登入即可執行任意 SQL |
| 既有資料卷沿用舊密碼 | 密碼只在資料卷第一次建立時生效，舊環境要手動改（見 `.env.example`） |

> 專案本身**沒有注入類漏洞**（SQL 全部參數化、無 `eval`/`exec`、MQTT 用 `json` 而非 `pickle`）。

### 🟠 接真實感測器前必做

| 項目 | 說明 |
|---|---|
| **RMS 去直流 + 帶通 10~1000 Hz** | 目前 RMS 含直流；ISO 20816 的 mm/s RMS 是交流量且限定頻帶 |
| **向量和 → 單軸最大** | ISO 評估取各方向最大值；向量和會過敏最多 1.73 倍 |
| **啟動抑制 / 穩態閘** | 真實機台過臨界轉速時振動達平常 5~10 倍，固定門檻會每次開機誤跳 |
| **感測器有效性檢查** | 加速度計掉線讀 0 → 永遠不跳且無人知曉（靜默失敗） |

### 🟡 功能增強

| 項目 | 依據 |
|---|---|
| 加 ALARM 級（目前只有 Trip） | ISO 20816-1：ALARM 設在「基線 + 25% × Zone B 上限」 |
| ISO 13374 第 4 層：健康評估/診斷 | 目前能說「異常」和「還剩多久」，說不出「是什麼故障」 |
| ISO 13374 第 6 層：建議生成 | 目前只丟 CRITICAL 給人，沒有維修建議 |
| 觀測占空比 | 目前每 10 秒只看 2 秒（20%），可改用連續彙總達 100% |

### 訓練資料保存

`sensor_readings` 只保留 20 分鐘，**必須在機台確認健康時主動存下來，事後無法回溯**。

| 層級 | 大小 | 指令 |
|---|---|---|
| 不保存 | 0 | `trainer.py --all --force`（健康時直接重訓） |
| 特徵矩陣 | 全機隊 **420 KB** | `trainer.py --all --force --save-features DIR` |
| 原始波形 | 5 分鐘約 **420 MB** | `tools/export_baseline_snapshot.py --minutes 5` |
