3. **參數要有外部依據，並在機隊尺度驗證** — 單通道看起來安靜的門檻，乘上 60 通道可能就是告警洪水。

# 改動一：CUSUM 偵測強化

## 背景問題

原本 `h = CUSUM_H_MULT * sigma0` 是**固定** 8σ₀，`value > h` 才報漸進劣化。兩個實際毛病：

1. **緩慢劣化 onset 太晚亮**：CUSUM 累積值爬得慢，固定 8σ₀ 要拖到接近末期才跨得過去。
2. **σ₀ 被高估就永不觸發**：暖機期若碰到吵的一段，σ₀ 偏大 → h 在絕對值上過大。V05-X 就是這樣，
   thd 已飆到 0.099 但 CUSUM 從未觸發，當時只好臨時加 `THD_ONSET_FLOOR` 補丁繞過。

實作時發現：**門檻是由 σ₀ 推導的，所以 σ₀ 的估計品質才是真正的瓶頸**。因此最後做成三層
（1-A 門檻、1-B 校準品質、1-C 校準持久化），外加一個量測工具（1-D）。

---

## 1-A 門檻衰減 + 地板

### 公式前後對照

**改動前**（`CusumTracker.update`，校準完成時設定一次）：

```python
self.h = CUSUM_H_MULT * self.sigma0        # 固定 8σ₀，設定後永不改變
```

**改動後**，拆成兩階段：

① 校準時只設定「起始值」與「地板」（`_apply_baseline`）：

```python
self.h_start = CUSUM_H_MULT * self.sigma0                    # 8σ₀ —— 現在只是起點
self.h_floor = min(self.h_start, floor_mult * self.sigma0)   # 7σ₀（低信心時 8σ₀）
self.h       = self.h_start
self._n      = 0                                             # 衰減時鐘歸零
```

② 每次 `update()` 才算出「當下生效的 h」：

```python
steps  = self._n // CUSUM_DECAY_PERIOD_SAMPLES
self.h = max(self.h_floor, self.h_start * (CUSUM_DECAY_FACTOR ** steps))
```

完整公式：

```
h = max( 7σ₀ ,  8σ₀ × 0.8^⌊n/70⌋ )
      地板        起始      衰減步數（n = 校準後樣本數）
```

> **注意**：`CUSUM_H_MULT` 的語意變了 —— 從「決策門檻倍率」變成「**起始**門檻倍率」。
> 變數名沿用未改，但註解已改寫。

### 實際數值走勢

| 校準後樣本數 | 時間（@30s/筆） | `8σ₀ × 0.8^步` | **生效 h** |
|---|---|---|---|
| 0~69 | 0~35 分 | 8.00σ₀ | **8.00σ₀** |
| 70~139 | 35~70 分 | 6.40σ₀ | **7.00σ₀**（被地板擋住） |
| 140+ | 70 分以後 | 5.12σ₀ ↓ | **7.00σ₀**（永遠停在地板） |

實務上是「**8σ₀ 跑 35 分鐘 → 之後固定 7σ₀**」。因為 8×0.8=6.4 已低於地板 7，衰減實際只走一階。
仍達成原始目的（8σ→7σ 約 7 倍 ARL 靈敏度改善），若要更漸進的曲線可把 `CUSUM_DECAY_FACTOR`
調成 0.95 之類（env 可調）。

`_apply_baseline` 每次呼叫都把 `_n` 歸零 → **重新校準時衰減時鐘重來**，不沿用舊進度。

### 參數取值理由

| 參數 | 值 | 理由 |
|---|---|---|
| `CUSUM_H_MULT` | 8.0 | 起始值。沿用原本已實測穩定的保守值，不動它 |
| `CUSUM_DECAY_FACTOR` | 0.8 | 需求指定 |
| `CUSUM_DECAY_PERIOD_SAMPLES` | 70 | CUSUM 每輪一筆、每輪約 30s → 70 筆 ≈ 35 分鐘。**用樣本數而非牆鐘**，重放測試才能重現 |
| `CUSUM_H_FLOOR_MULT` | **7.0** | 見下節，這是最重要也最曲折的一個 |

### 地板 7σ 的來歷（中途修正過一次）

**第一版訂 5σ —— 這是錯的。** 當時只用 Siegmund 近似算**單通道** ARL（k=0.5），
每降 1σ 假警間隔約縮 3 倍（8σ≈19000 樣本、5σ≈940、3σ≈120），覺得 5σ「還算安靜」。

**錯在沒把機隊尺度乘進去。** 操作員感受到的不是單一通道，而是 **60 個通道**（6 通道/台 × 10 台）
同時跑，機隊告警率 = 單通道率 × 60。

查 ISA-18.2 才拿到客觀標準：穩態下每位操作員應 **< 6 則告警/小時**，> 30 則/小時視為告警洪水。
用 `cusum_false_alarm_replay.py` 實測（60 通道 × 720 小時）換算：

| 地板 | 單通道假警間隔 | **機隊告警率** | ISA-18.2 判定 |
|---|---|---|---|
| 5σ | 3.2 小時 | **18.6 則/小時** | ⚠️ 超標 |
| 6σ | 10.2 小時 | 5.9 則/小時 | 壓線（vs 上限 6.0），無餘裕 |
| **7σ（採用）** | 19.5 小時 | **3.1 則/小時** | ✅ 約 2 倍餘裕 |
| 8σ | 15.3 小時 | 3.9 則/小時 | ✅（與 7σ 的差異屬蒙地卡羅雜訊） |
| 9σ | 20.2 小時 | 3.0 則/小時 | ✅ |

**教訓：調告警門檻必須換算成機隊尺度，不能只看單通道。**

> 另註：「離線實驗 3~12σ 都能 17/17 命中」講的是**偵測力**（會不會抓到），不是**誤報率**。
> 那個實驗跑的是必然會壞的 run-to-failure 資料，量不到「健康通道亂報」。不能拿來當「3σ 安全」的依據。

## 1-B robust 校準（方案 ②+①）

### 問題

原本 `mu0=mean(暖機)`、`sigma0=std(暖機)`。**mean/std 的崩潰點是 0% —— 一顆離群值就能拉歪。**

工廠暖機那 10 分鐘必然混進瞬態：負載尖峰、鄰機干擾、單筆壞值、電氣突波、換產品 blip。
mean/std 被灌大 → h 變大 → **CUSUM 遲鈍漏抓真故障**（這正是 V05-X 的機制）。

### 方案選擇：為什麼是「②+①」而不是單用 median/MAD 或雙 tracker

考慮過三種「同時使用兩組統計」的做法：

| 方案 | 做法 | 評價 |
|---|---|---|
| ① 交叉檢查閘 | 兩組都算，互相當品質偵測器 | 便宜、CP 值高，但本身不改善估計 |
| **② robust 修剪→古典估計** | 先用 median/MAD 擋離群，再在乾淨點上用 mean/std | **採用**：兼得 robust 與效率 |
| ③ 雙 tracker 並聯 | 跑兩個 CUSUM 再 AND/OR 合警報 | 成本雙倍；AND 會繼承較遲鈍者的缺點，不划算 |

採用 **②（主力）+ ①（品質旗標）**。理由：
- 單用 median/MAD 的代價是**效率低**（MAD 相對效率約 0.37，要約 2.7 倍樣本才達同等穩定度），
  在只有 20 筆暖機時 σ₀ 本身會抖。
- ② 先剔除離群再用 mean/std，**乾淨點上享 std 的效率、髒點被 MAD 擋掉**，補掉了這個缺點。
- ① 的分歧訊號幾乎零成本，直接變成「這條基線可不可信」的旗標。

### 實作（`CusumTracker._calibrate`）

```python
med       = median(warmup)
mad_sigma = 1.4826 * median(|warmup - med|)          # 換算成常態等價 σ
scale     = max(mad_sigma, CUSUM_SIGMA_FLOOR)

keep = warmup[ |warmup - med| <= CUSUM_TRIM_K * scale ]   # robust 修剪
if len(keep) >= min_keep:
    mu0, sigma0 = mean(keep), max(std(keep), CUSUM_SIGMA_FLOOR)   # 乾淨點用古典估計
else:
    mu0, sigma0 = med, scale                                       # 污染過重就退回 robust

low_confidence = (|mean(全體) - med| > 0.5*scale)      # ① 交叉檢查閘
              or (std(全體) > 1.5*scale)
              or (剔除比例 > 0.3)
floor_mult = 7.0 + (1.0 if low_confidence else 0.0)
```

### 參數取值理由

| 參數 | 值 | 理由 |
|---|---|---|
| `CUSUM_TRIM_K` | **4.0** | 修剪門檻取**寬鬆**值。健康分數本身有不對稱的向下深谷（實測最差 −0.72），K 太小（2~3）會誤砍這些「深但健康」的樣本 → σ₀ 縮小 → **反而更會誤報**。只砍極端瞬態 |
| `CUSUM_MIN_KEEP` / `_FRAC` | 10 / 0.5 | 剔太兇代表污染過重，此時不硬算古典估計，退回全體 robust 值 |
| `CUSUM_GATE_SHIFT` | 0.5 | mean 與 median 差超過 0.5×scale → 資料偏斜 |
| `CUSUM_GATE_RATIO` | 1.5 | std/MAD 比超過 1.5 → 重尾/污染（常態下此比值應接近 1） |
| `CUSUM_GATE_REJECT_FRAC` | 0.3 | 剔除超過 30% → 這段暖機不乾淨 |
| `CUSUM_LOWCONF_FLOOR_BUMP` | 1.0 | 低信心時地板 +1σ（=8σ，等同不衰減）。可疑基線不該隨時間變更敏感 |
| `CUSUM_SIGMA_FLOOR` | 0.05 | 保留原值。MAD 可能為 0（分數量化、感測器卡住），這個下限兜底，**用 MAD 後更形重要** |

### 已知限制

- MAD 是**繞中位數對稱**算的，而 CUSUM 只在意**向下**穿越。健康分數的向下肥尾會被低估 →
  σ₀ 偏小。若日後觀察到健康下探誤報，正解是改用**單邊（向下）robust 散布**，比對稱 MAD 更貼合。
- robust 校準只擋**少數**污染。若暖機期間機台**過半已在劣化**，它跟 mean/std 一樣會校準到劣化態。
  它補強、但不取代「在確認健康的一段校準」這件紀律。

### 實測

| 情境 | robust σ₀ | 舊 mean/std σ₀ | 判定 |
|---|---|---|---|
| 乾淨高斯暖機 | 0.085 | 0.085 | **完全一致 → 不退化** |
| 污染（20 筆插 3 筆 −1.0 尖峰） | **0.075** | **0.294**（3.9×） | robust 守住；自動標低信心、抬高地板 |

## 1-C 基線持久化

### 問題

`mu0/sigma0` 原本只活在記憶體，服務一重啟就重新暖機 → **每次重啟盲窗 10~25 分鐘**
（暖機期 CUSUM 回 `(None, False)`，對漸進劣化是瞎的）。工廠一天重啟數次（換班、保養、跳電、
部署、DB 重連），盲窗會反覆累積。

### 為什麼不是「把暖機拉長」

`CUSUM_WARMUP_SAMPLES` 20→100 確實能把假警 ARL 從 448 拉到 5250，但工廠實務上有四個代價：

1. **每次重啟都要重付更長的盲窗**（50 分鐘 vs 10 分鐘）。
2. **「暖機資料必須健康」的假設，窗越長越難成立** —— 負載變動、換產品、機台熱機都會進來，
   σ₀ 被正常運轉變異灌大 → CUSUM 反而遲鈍。
3. **間歇/批次型機台可能永遠校準不完** —— 單次運轉短於暖機時長就拿不到偵測器。
4. **上線/調機摩擦** —— 裝好後 50 分鐘才有第一個訊號。

所以正解是「**一次乾淨的校準 + 持久化**」，而不是「每次都花更久暖機」。

### 實作

新增 `cusum_baselines` 表（device/sensor 為 PK，最多 60 列，非 hypertable）：

| 欄位 | 用途 |
|---|---|
| `mu0` / `sigma0` | 健康基線 |
| `low_confidence` | 校準可信度 |
| `rejected_frac` / `n_warmup` | 稽核用 |

- **存**：現場乾淨暖機完成就 upsert；**低信心的不存**（避免把可疑基線傳給下次）。
- **載**：重啟時 `load_baseline()` 載回 → **立刻 calibrated、零盲窗**。
- `init.sql` 與 ai_service 啟動時都 `CREATE TABLE IF NOT EXISTS`，對既有 DB 安全。

### 關鍵風險與再驗證機制

**SVM 模型每次啟動都重訓，分數尺度可能微漂移** —— 直接套用舊基線會失準。
所以載入後進「再驗證期」：

```
載入基線 → calibrated=True（照常偵測，零盲窗）
         → 收集 10 筆新分數
         → |median(新分數) - 載入的 mu0| <= 3σ ?
              是 → 確認採用
              否 → 丟棄基線、退回重新暖機（自我修復，設 reval_failed 旗標）
```

| 參數 | 值 | 理由 |
|---|---|---|
| `CUSUM_REVALIDATE_SAMPLES` | 10 | 夠估中位數，又只花約 5 分鐘 |
| `CUSUM_REVALIDATE_TOL` | 3.0 | 3σ 是常態下的常規離群界，健康波動不會誤判為漂移 |

`main.py` 用 `tracker.calib_generation`（每完成一次校準 +1）偵測「剛校準」事件，確保記錄/存檔
每次校準只做一次，含重新校準。

### 實測

| 情境 | 結果 |
|---|---|
| 有效基線 | 載入後立刻 `calibrated=True`（零盲窗），再驗證一致 → 採用 |
| 漂移基線（載入 mu0=−0.2，新分數實際在 −0.6） | 觸發 `reval_failed` → 退回暖機 → 最終校準到正確的 mu0=−0.622 |
| 正式環境 | 重啟後 log 出現 `CUSUM 基線已載回（跳過暖機、再驗證中）` |

### 尚未做（工廠實務加分項）

- 校準**只在穩態時收樣**（gate on 額定轉速/負載），避免熱機與換產品污染。
- **多運轉模式各存一組基線**。

## 1-D 假警重放工具

新增 `validation/cusum_false_alarm_replay.py`：拿健康分數餵進**正式服務用的同一個 `CusumTracker`**
（含衰減、robust 校準），掃不同地板數假警。

- `gauss` 分布 = 保守上界；`tight`（輕下尾）= 貼近實測有界分數。
- `--scores` 可餵真實 `anomaly_scores.score` 做定論測試。
- **內建 ISA-18.2 判定欄**：自動把單通道假警率 × 通道數換算成機隊告警率，並標示合格/偏高/告警洪水。

### 量測慣例（兩個容易做錯的地方）

1. **首次穿越**：onset 在正式服務只觸發一次，所以「這條健康通道會不會誤報」看的是第一次
   `is_degrading=True` 的時刻。
2. **警報後重啟**：CUSUM 跨門檻後 `value` 不會自己歸零、會連續多輪都 True。直接數樣本會爆
   （第一版就這樣，假警數比理論高 650 倍）。算 ARL 必須每次警報後把 `value` 重置為 0。

### 最大產出：一個反直覺的發現

**假警率的主導變數是「暖機筆數」，不是地板。** 固定 8σ 下實測 ARL 隨暖機長度：

| 暖機筆數 | 實測 ARL | 對照理論上限 |
|---|---|---|
| 20（現行） | 448 | 19,112 |
| 50 | 2,441 | |
| 100 | 5,250 | |
| 300 | 10,527 | |
| 1000 | 14,185 | |

只有 20 筆時 σ₀/μ₀ 估不準，而 ARL 對 h/σ 是**指數敏感**，校準偏差把假警放大約 40 倍。
這也是 1-B（robust 校準）與 1-C（持久化，讓一次長校準能反覆沿用）真正的價值所在。

# 改動二：振動時域跳線（災難兜底）

## 定位（先講清楚，否則參數會選錯）

這是**告警兜底，不是跳機保護**。真正的機械保護是 API 670 系統（硬接線、2oo3 表決、SIL 認證、
毫秒級響應），軟體輪詢資料庫做不到那件事。所有參數都照「告警」這個定位選（30~60 秒等級），
而不是保護跳機的 1~3 秒。

## 為什麼需要它

SVM 是「相對於學到的正常」的模型。若某通道模型沒訓練成功、或不幸在已劣化資料上訓練（學歪基線），
一個物理上的嚴重超標它可能整個漏掉。硬門檻**不依賴 ML**，再爛的模型也擋不住這條。

分工乾淨：
- **SVM/CUSUM** 抓「振幅還沒動、頻譜先變」的**早期**劣化。
- **時域跳線** 抓「振幅已經爆掉」的**末期/突發**災難。

## 判定邏輯

```
三軸 RMS 合成幅值 = sqrt(rmsX² + rmsY² + rmsZ²)
若 >= machine_vibration_thresholds.danger_lower  →  強制 CRITICAL（不看 SVM/CUSUM）
```

**門檻不是寫死的**，按機台 Class 從 DB 讀：

| Class | 機台 | `danger_lower` (mm/s) |
|---|---|---|
| I | SCT-01~06 | 4.5 |
| II | SCT-07~08 | 7.1 |
| III | SCT-09~10 | 11.2 |

- **為何用 RMS 而非峰值**：ISO 20816 的分區限值就是定義在寬頻 RMS 速度上，規範明講
  「峰值或窄頻讀數不可直接與這些限值比較」。
- **為何用向量和**：因為模擬器就是用向量和產生目標幅值、門檻表也照這個口徑建，內部自洽。
  （**接真實感測器要改** —— 見文末待辦。）

## 四道護欄

| 護欄 | 參數/機制 | 值 | 理由 |
|---|---|---|---|
| **解耦** | `VIB_TRIP_CHECK_INTERVAL` | **10 秒** | 保險絲只需要 RMS（極廉價），不該被昂貴的 FFT/SVM 週期（30s）拖慢或餓死。跑**獨立執行緒 + 獨立連線** |
| **去抖動** | `VIB_TRIP_DEBOUNCE_CYCLES` | **3**（→30 秒） | 防單發瞬態。API 670 用 1~3 秒延遲濾突波是同一原理，但那是硬體連續監測；軟體 CM 系統告警延遲典型 10~60 秒，30 秒落在合理帶 |
| — | `VIB_TRIP_WINDOW_SECONDS` | **2.0** | 與原本 SVM 特徵窗（4096 點 @2kHz ≈ 2.05s）同口徑，查詢成本已知可行 |
| **遲滯** | `VIB_TRIP_RESET_RATIO` | **0.9** | ISA-18.2 要求死區防抖動 —— 振動在門檻附近徘徊會 trip/clear 反覆跳。10% 死區是製程告警常規值 |
| **閂鎖** | `vib_trip_latches` 表 | 至人工確認 | ISA-18.2 告警語意：**條件解除與人工確認缺一不可**才復歸。災難事件的紀錄不該自己消失 |
| **fail-safe** | 三軸沒湊齊 / 無門檻 | 跳過 | 寧可不跳，也不因缺資料誤跳或崩潰 |

### 狀態機

```
正常 ──(連續3輪超標)──> 跳閘+閂鎖(未確認) ──(人工確認)──> 已確認，等待復歸
                                                              │
                                    ┌─────────────────────────┘
                                    ▼
                          振動 < 門檻×0.9 ？
                              是 → 清除閂鎖，復歸正常
```

## 過程中抓到的兩個 bug

| # | 問題 | 嚴重度 |
|---|---|---|
| 1 | `LIKE 'V%'` 的 `%` 被 psycopg2 當成參數佔位符 → `IndexError: tuple index out of range` | 中（功能不通） |
| 2 | 只 `except psycopg2.Error`，`IndexError` 逃逸 → **執行緒靜默死亡，之後完全沒有跳線保護且無人知曉** | **高** |

Bug 2 的教訓：**安全兜底靜默死亡是最糟的失效模式** —— 比沒有這道保險絲更危險，因為它讓人
誤以為有保護。修法：捕捉所有 `Exception`，記錄後重連續跑。

修正：
```python
# 前
WHERE sensor_id LIKE 'V%' AND ts > now() - (%s * interval '1 second')
except psycopg2.Error as exc:

# 後
WHERE sensor_id LIKE 'V%%' AND ts > now() - (%s * interval '1 second')
except Exception as exc:        # 刻意捕捉所有例外
```

# 附帶：RUL 信賴區間（ISO 13381-1）

嚴格說不屬於上述兩個改動，但同批完成，列此備查。

**動機**：ISO 13381-1 要求預後結果必須附信賴區間、不能只給點估計。我們的 RUL 相對誤差 60~70%，
只報一個數字會誤導。

**作法**：RandomForest 的 120 棵樹各自是一個獨立預測，**取樹分布的分位數就是「免費」的預測區間**，
不需重訓或另建模型：

```python
tree_preds = np.array([est.predict(X)[0] for est in _RUL_MODEL.estimators_])
p10, p90 = np.percentile(tree_preds, [10, 90])
```

非樹系模型（日後換 LSTM）會 `AttributeError` → 捕捉後回 None，不讓服務掛掉。

**儲存**：`rul_predictions.eta_p10_seconds` / `eta_p90_seconds`（`init.sql` 有 `ALTER ... IF NOT EXISTS`）。
Grafana 面板 60 加 P10/P90 欄、面板 61 改畫「點估計 + P10/P90 虛線帶」。

**實測行為 —— 劣化越明顯，區間越窄**：

| 狀態 | rms_norm | P10~P90 | 區間寬度 |
|---|---|---|---|
| 健康 | 1.00 | 190~241 | 51 分 |
| 劣化中 | 1.70 | 109~139 | **30 分** |

訊號變強 → 模型信心提高。這正是信賴區間該有的行為。

## 踩過的坑：判定基準不能隨便改成 P10

一度把 `ML_RUL_STATUS_QUANTILE` 預設為 `'p10'`（想抵銷「模型末期高估 RUL」的已知失效模式 ——
IMS 0~30 分帶平均高估 47 分）。結果：**健康態 P10=190 < WARNING 門檻 200 → 30 個通道全部常駐
WARNING**，反而違反剛用 ISA-18.2 修好的原則。

原因：200/60 這組門檻是為**點估計**校準的。故預設維持 `'mean'`；若要改 `'p10'`，
必須同時把 `ML_RUL_WARNING_MIN` ≈ 170、`ML_RUL_CRITICAL_MIN` ≈ 50 一起重新校準。

**教訓：改判定基準要連門檻一起重校，且要先在健康態量過再定預設。**

# 待辦

## 接真實感測器前**必做**（目前僅在模擬器內部自洽）

| # | 項目 | 說明 |
|---|---|---|
| 1 | **RMS 去直流 + 帶通 10~1000 Hz** | 目前 `rms = sqrt(mean(values²))` **含直流**（`spectral_features.py`，FFT 有去均值、RMS 沒有）。ISO 20816 的 mm/s RMS 是交流量且限定 10~1000 Hz。真實加速度計還需先積分成速度 |
| 2 | **向量和 → 單軸最大** | ISO 20816 評估的是「各方向量測值中的**最大者**」。三軸相等時向量和是單軸的 √3≈1.73 倍 → 拿向量和比 ISO 限值會**過敏最多 1.73 倍** |
| 3 | **啟動抑制 / 穩態閘** | 真實機台通過臨界轉速時振動可達平常 5~10 倍，固定絕對門檻會**每次開機誤跳**。ISO 20816 只適用「額定轉速穩態」。建議啟動後 60~120 秒抑制 + 轉速/負載閘 |
| 4 | **感測器有效性檢查** | 加速度計掉線通常讀 0 → RMS=0 → 永遠不跳且無人知曉（靜默失敗）。工廠做 IEPE 偏壓檢查（8~12V 正常、0V 短路、24V 斷線），軟體端至少要有「太安靜」告警 |
| 5 | **振動取樣率：2kHz 不夠** | 模擬器的 2kHz 對真實加速度計有兩個問題：① **ISO 頻帶上緣量不完整** —— Nyquist 剛好 1kHz，抗混疊濾波器的過渡帶會吃掉 1000Hz 附近，10~1000Hz 實際上量不滿，而且需要硬體抗混疊濾波，否則高頻能量會混疊進來；② **做不了軸承包絡分析** —— 軸承缺陷衝擊激發的是數 kHz 的結構共振頻帶，要先在那個頻帶解調才看得到 BPFO/BPFI。公開軸承資料集約為 12~100kHz 取樣（CWRU 12/48k、XJTU-SY/PHM2012 25.6k、Paderborn 64k、MFPT 約 97.7k），所以**故障診斷演算法要在資料集的原生取樣率上開發驗證，不要先降到 2kHz**。接真實感測器時二選一：(a) 提高振動通道取樣率（建議 ≥ 20kHz），但「全量原始資料寫 DB + 中央算 FFT」的架構已在 4kHz 就把 CPU 壓垮（見 `project-report.md` §9.1），不能直接放大；(b) **在邊緣端計算 RMS、包絡頻譜等特徵，只上傳特徵**，原始波形只在觸發時保存片段。建議採 (b)。電流通道（MCSA 看 60Hz 邊帶）維持 2kHz 即可 |

## 規範查閱找到的其他改進方向

| 優先 | 項目 | 依據 |

| 中 | 加 **ALARM 級**（目前只有 Trip） | ISO 20816-1：ALARM 設在「基線 + 25% × Zone B 上限」，且不超過 1.25× Zone B 上限。這是**相對基線**的，與既有 `rms_norm` 機制天生契合 |
